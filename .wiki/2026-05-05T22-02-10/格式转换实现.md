# 格式转换实现

`convert` 命令是 licon 中将 Lucide 图标从矢量格式（SVG）光栅化为位图格式（PNG/WebP）的唯一入口。它的实现巧妙地平衡了**功能完整**与**依赖轻量**两个目标，通过可选依赖模式将 sharp —— 一个体积约 50MB 的本地编译库 —— 从强制依赖降级为按需加载。

## 架构概览

整个转换流程可分解为三个阶段：

```mermaid
flowchart LR
    A[SVG Source] --> B{Format?}
    B -->|svg| C[文件复制]
    B -->|png| D[sharp(svg).png()]
    B -->|webp| E[sharp(svg).webp()]
    C --> F[写入文件系统]
    D --> F
    E --> F
```

核心源文件仅约 80 行，紧凑但覆盖了四个责任维度：可选依赖加载、格式分支调度、异步光栅化流水线、异常处理。[来源](src/commands/convert.ts#L1-L78)

## 可选依赖：sharp 的惰性加载

Sharp 是 Node.js 生态中最高效的图像处理库之一，但它依赖原生编译的 libv8 库，在 `npm install` 阶段可能因平台差异而失败。convert 命令的处理策略是**声明为依赖，运行时捕获**：

```typescript
let sharp: any = null;

try {
  sharp = require('sharp');
} catch (e) {
  // sharp not available
}
```

这段代码在模块顶层执行。`require('sharp')` 在 ESM 项目中以 CommonJS 兼容模式工作（整个项目使用 `"type": "module"`，但 `require` 仍可加载 CJS 模块）。如果 sharp 因任何原因无法加载 —— 编译失败、二进制不兼容、安装中断 —— `sharp` 变量保持 `null`，程序不崩溃。[来源](src/commands/convert.ts#L3-L8)

当用户请求 SVG 输出时，这个检查甚至不会被触发：代码在 `if (format === 'svg')` 分支中提前返回，完全绕过 sharp 的存在性判断。只有请求 PNG 或 WebP 时才执行：

```typescript
if (!sharp) {
  console.log('⚠️  sharp is not installed. Cannot convert to PNG/WebP.');
  console.log('   Install with: npm install sharp');
  process.exit(1);
}
```

这个模式的精妙之处在于：**同一个二进制包，在 SVG 模式下对用户完全透明；在光栅模式下给出清晰的故障引导**，而非抛出 `MODULE_NOT_FOUND` 式的原生错误。[来源](src/commands/convert.ts#L54-L58)

### 与 package.json 的张力

有趣的是，`sharp` 被声明在 `dependencies`（而非 `optionalDependencies`）中：

```json
"dependencies": {
  "sharp": "^0.33.0"
}
```

这意味着 `npm install` 默认会尝试编译 sharp，如果失败整个安装过程退出码非零。这是项目当前的设计权衡：**优先保证功能完整，依赖可选性由运行时容错兜底**。若要让安装永不失败，应将 sharp 移至 `optionalDependencies`。[来源](package.json#L19-L24)

## 格式分支：三种路径，两种本质

### SVG 格式——文件复制路径

当 `--format svg`（或默认无参）时，代码执行的是纯文件操作：

```typescript
if (format === 'svg') {
  const svg = fs.readFileSync(iconPath, 'utf-8');
  const destPath = path.join(outputDir, `${name}.svg`);
  fs.writeFileSync(destPath, svg);
  console.log(`Saved: ${destPath}`);
  return;
}
```

为什么 SVG 不经过 sharp？两个原因：

1. **语义完整**：SVG 是矢量格式，sharp 是光栅化引擎。让 sharp 读取 SVG 再写出 SVG 是无意义的编解码循环，可能引入精度损失（sharp 会解析 SVG 的 DOM 并重新序列化）。
2. **零依赖执行**：如前所述，SVG 分支允许用户在 sharp 未安装时仍能使用 `convert` 命令的完整功能。

事实上，这个分支与 `save` 命令的功能完全等价。[save 命令](src/commands/save.ts#L1-L26) 的执行逻辑与 `convert --format svg` 几乎一致 —— 后者只是多了一层格式判断的包装。[来源](src/commands/convert.ts#L35-L43)

### PNG 与 WebP——光栅化路径

这是 convert 命令的核心价值所在。两个分支共享同一模式：

```typescript
let buffer: Buffer;

if (format === 'png') {
  buffer = await sharp(svg).png().toBuffer();
} else if (format === 'webp') {
  buffer = await sharp(svg).webp().toBuffer();
}
```

`sharp(svg)` 接收的是 `fs.readFileSync(iconPath)`（注意，没有指定编码，返回 `Buffer` 而非字符串）。Sharp 内部使用 librsvg 解析 SVG 并将其渲染为原始像素矩阵，然后调用对应的编码器（libpng 或 libwebp）压缩输出。

`.png()` 和 `.webp()` 的调用值得注意：**它们都没有传入参数**。

| 格式 | 调用 | 默认参数含义 |
|------|------|-------------|
| PNG | `.png()` | 无压缩级别指定，使用 zlib 默认压缩（6）；无透明度优化；无调色板量化 |
| WebP | `.webp()` | 无质量参数指定，默认 quality=75；无损模式未开启 |

这意味着所有光栅化输出都使用 sharp 的出厂默认值。对于 Lucide 图标（通常为 24×24 的简单线条图形），这些默认值通常足够，但也意味着：

- 无法控制输出分辨率（默认 72 DPI，尺寸由 SVG 的 `viewBox` 决定）
- 无法进行 PNG 调色板量化（对纯色图标可显著减小体积）
- 无法设置 WebP 的 `nearLossless` 或 `alphaQuality` 参数

如果需要这些控制，扩展 `convert` 的 options 接口即可。[来源](src/commands/convert.ts#L65-L72)

### 未识别格式的兜底

```typescript
} else {
  console.error(`Unsupported format: ${format}`);
  console.log('Supported formats: svg, png, webp');
  process.exit(1);
}
```

这是一个防御性分支，尽管 Commander.js 的 option 定义理论上限制了输入。它保证了未来如果通过编程方式（而非 CLI 解析）调用时，格式验证仍然存在。[来源](src/commands/convert.ts#L73-L77)

## 异步 Buffer 转换流程

整个转换的核心可抽象为一条数据流：

```
SVG Buffer → sharp() → [解析 + 光栅化] → PNG/WebP 编码 → Buffer → fs.writeFileSync
```

关键点在于 `sharp(…).png().toBuffer()` 返回的是一个 `Promise<Buffer>`，因此外层 `convertCommand` 函数是 `async` 的，调用方（`index.ts`）使用 `await` 等待完成：

```typescript
// index.ts
.action(async (name, options) => {
  const config = getConfig();
  await convertCommand(name, options, config);
});
```

之所以在 `convert` 命令中使用 `toBuffer()` 而非 `toFile()`，是为了在写入前统一错误处理：无论解码失败还是编码失败，都被同一个 `try/catch` 捕获。[来源](src/index.ts#L74-L78)

## 异常处理层级

convert 命令的异常处理分为三层：

**第一层：前置条件检查**
```typescript
if (!config.repoPath) { if (!ensureSetup()) { return; } }
if (!fs.existsSync(iconPath)) { console.error(...); process.exit(1); }
```
通过 `ensureSetup()` 触发配置向导，通过 `fs.existsSync` 验证图标存在。

**第二层：依赖检查**（前文已述）

**第三层：运行时错误**
```typescript
try {
  // sharp conversion
} catch (err: any) {
  console.error(`Failed to convert: ${err.message}`);
  process.exit(1);
}
```
sharp 转换可能因多种原因失败：SVG 语法异常、内存不足、编码器内部错误。这些都被统一转化为用户友好的错误消息，阻止堆栈泄露到终端。[来源](src/commands/convert.ts#L64-L82)

## 与 save 命令的关系

`convert` 和 `save` 在功能上有显著重叠：

| 维度 | `save` | `convert` |
|------|--------|-----------|
| 输入格式 | SVG | SVG |
| 输出格式 | SVG | SVG / PNG / WebP |
| 依赖 sharp | 否 | 仅 PNG/WebP 需要 |
| 同步/异步 | 同步 | SVG 同步，PNG/WebP 异步 |
| 默认输出 | cwd/<name>.svg | cwd/<name>.svg |

从架构角度看，`save` 是 `convert --format svg` 的**特化语法糖**。两者的 SVG 分支代码几乎相同。如果未来需要重构，完全可以让 `saveCommand` 内部委托给 `convertCommand`，避免代码重复。[来源](src/commands/save.ts#L1-L26)

## 命令注册与输入验证

在 `index.ts` 中，convert 命令注册为：

```typescript
program
  .command('convert <name>')
  .description('Convert icon to different format (png, webp, svg)')
  .option('-f, --format <format>', 'Output format: png, webp, svg (default: svg)')
  .option('-o, --output <path>', 'Output directory (default: current directory)')
  .action(async (name, options) => { ... });
```

与 `get` 命令（接受 `names...`，变长参数）不同，`convert` 的 `<name>` 是**单数必选参数** —— 一次只能转换一个图标。这是合理的限制：PNG/WebP 转换是计算密集型操作，批量处理应通过循环在调用侧（Shell 或 Agent）实现。[来源](src/index.ts#L68-L79)

## 局限性与改进方向

当前实现有几个值得注意的约束：

1. **无分辨率控制**：所有输出固定为 SVG 的原始 `viewBox` 尺寸（通常 24×24）。对于需要大尺寸图标的场景（如缩略图、社交卡片），应增加 `--size` 或 `--scale` 参数，对应 sharp 的 `resize()` 调用。

2. **无质量参数**：WebP 和 PNG 的编码参数全部使用默认值。加入 `--quality` 参数可释放 sharp 的编码潜力。

3. **单图标限制**：不支持 `convert icon1 icon2 --format png` 的批量模式。

4. **Sharp 的依赖状态模糊**：将 sharp 移至 `optionalDependencies` 可让安装永不失败，同时运行时仍保留当前的可选检测逻辑。
