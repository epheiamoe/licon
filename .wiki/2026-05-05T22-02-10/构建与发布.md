# 构建与发布

licon 从 TypeScript 源码到可执行 CLI 工具，再到 npm 包公开发行，整个流程由三个关键文件驱动：`package.json` 定义脚本和元数据，`tsconfig.json` 配置编译策略，`.gitignore` 和 `publishConfig` 控制发布范围。理解这条管线，你就掌握了如何让一个 TypeScript CLI 项目触达终端用户的完整路径。

## 编译管线：从 `src/` 到 `dist/`

licon 使用 TypeScript 官方编译器 `tsc` 将 `src/` 目录下的 `.ts` 文件编译为 `dist/` 目录下的 `.js` 文件。构建脚本极其简洁：

```json
"build": "tsc"
```

运行 `npm run build` 等价于执行 `tsc` 读取 `tsconfig.json` 中的配置进行编译。[来源](package.json#L14-L14)

### tsconfig.json 编译策略

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "node",
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
```

[来源](tsconfig.json#L1-L14)

这套配置中的几个关键选择需要理解：

| 选项 | 值 | 含义与后果 |
|------|-----|-----------|
| `target` | `ES2022` | 生成的 JS 代码使用 ES2022 语法特性，如类的静态初始化块、`Array.fromAsync` 等。Node.js 18+ 原生支持。 |
| `module` | `ESNext` | 输出 ES Module（`import`/`export`）语法，而非 CommonJS 的 `require()`。这与 `package.json` 中的 `"type": "module"` 一致。 |
| `moduleResolution` | `node` | 模块解析策略遵循 Node.js 规则，查找 `node_modules` 和文件扩展名。 |
| `rootDir` / `outDir` | `./src` → `./dist` | 源码与输出的目录结构镜像映射。`src/commands/get.ts` 编译为 `dist/commands/get.js`。 |

值得注意的是，`"module": "ESNext"` 意味着编译后的 `.js` 文件保留 `import` 语句——这在 Node.js 的 ESM 模式下完全可行，因为 `package.json` 声明了 `"type": "module"`。licon 没有使用打包器（如 webpack 或 esbuild），也没有将代码打包成单一文件，而是保持多文件模块结构，依赖 Node.js 运行时自行解析模块图。

## bin 字段：让 `licon` 命令全局可用

```json
"bin": {
  "licon": "./dist/index.js"
}
```

[来源](package.json#L8-L10)

当用户全局安装（`npm i -g @epheiamoe/licon`）时，npm 会在全局 `bin/` 目录下创建一个名为 `licon` 的符号链接，指向 `./dist/index.js`。`dist/index.js` 的第一行是 shebang：

```ts
#!/usr/bin/env node
```

[来源](src/index.ts#L1-L1)

这行 shebang 告诉操作系统使用 Node.js 来执行该文件。因此用户只需在终端输入 `licon get ...` 即可运行，无需显式调用 `node`。

> 关于命令注册和调度机制的细节，参见 [命令注册与调度](命令注册与调度.md)。

## 生命期脚本：自动构建策略

licon 定义了两个 npm 生命期脚本，确保从安装到发布的每个环节产出的都是最新代码：

### prepack：发布前自动构建

```json
"prepack": "npm run build"
```

[来源](package.json#L15-L15)

当执行 `npm pack` 或 `npm publish` 时，npm 在打包前自动触发 `prepack` 脚本。这意味着你永远不需要手动 `npm run build` 后再发布——`prepack` 保证 `dist/` 目录始终与 `src/` 同步。这条脚本是在 1.0.1 版本迭代中加入的，此前发布时需要手动构建，容易遗漏。[来源](https://github.com/epheiamoe/licon/commit/1ae8cd2)

### postinstall：安装后自动编译

```json
"postinstall": "npm run build || echo 'Build failed - run: npm run build'"
```

[来源](package.json#L16-L16)

当用户执行 `npm install`（无论是全局安装还是作为依赖安装）时，npm 在包安装完成后自动运行 `postinstall` 脚本。licon 的 `postinstall` 尝试运行 `tsc` 编译：

- **成功**：编译完成，`dist/` 目录可用，用户可以立即使用 `licon` 命令。
- **失败**：输出警告信息 `Build failed - run: npm run build`，但安装不会中断（`||` 后的 `echo` 确保退出码为 0）。

这种设计允许源码分发包通过 npm 分发，让安装流程在用户本地完成编译——但这也意味着用户本地必须安装 TypeScript 编译工具链。如果 `postinstall` 编译失败，用户只需手动执行 `npm run build` 即可。

### 构建产物与版本控制

`.gitignore` 将 `dist/` 目录排除在版本控制之外：

```
dist/
```

[来源](.gitignore#L2-L2)

这意味着 Git 仓库中只维护 TypeScript 源码，构建产物由 `postinstall` 或 `prepack` 在本地生成。你克隆仓库后需要执行 `npm install` 才能获得可运行的 `dist/` 目录。

## 发布流程：将 licon 推送到 npm

licon 的 npm 包名为 `@epheiamoe/licon`，属于 npm 作用域包（scoped package）。完整发布步骤如下：

### 1. 构建

在发布前确保代码通过编译：`npm run build`。实际上 `prepack` 脚本会自动完成这一步，但提前验证可以尽早发现问题。

### 2. 更新版本号

```bash
npm version patch   # 补丁更新: 1.0.0 → 1.0.1
npm version minor   # 次要更新: 1.0.0 → 1.1.0
npm version major   # 主要更新: 1.0.0 → 2.0.0
```

`npm version` 命令会自动更新 `package.json` 中的 `version` 字段，并创建对应的 Git 标签。

### 3. 发布

```bash
npm publish --access public
```

由于 `@epheiamoe/licon` 是作用域包，默认情况下 npm 认为它是私有的（需要付费账户）。加上 `--access public` 标志明确声明为公开包，免费账户即可发布。

### 4. publishConfig：固化发布参数

```json
"publishConfig": {
  "access": "public"
}
```

[来源](package.json#L11-L13)

`publishConfig` 将发布参数固化在 `package.json` 中。设置之后，后续发布只需运行 `npm publish`（无需每次手动添加 `--access public`），而且还支持其他参数如 `tag`、`registry` 等。这在 CI/CD 自动化和多人协作场景下尤其有用——消除了因忘记传参导致发布失败的可能性。

### 完整的发布命令示例

```bash
# 更新版本
npm version patch

# 发布（prepack 会自动执行 npm run build）
npm publish --access public

# 推送 Git 标签
git push --follow-tags
```

## 依赖结构：运行时 vs 开发时

`dependencies`（运行时依赖）会在用户安装包时自动下载，而 `devDependencies`（开发依赖）只在开发本地方便使用。[来源](package.json#L18-L23)

| 依赖类型 | 包含 | 用途 |
|---------|------|------|
| `dependencies` | `chalk`, `commander`, `fuzzy`, `sharp` | 运行时实际调用的库：终端着色、CLI 框架、模糊搜索、图像转换 |
| `devDependencies` | `@types/node`, `typescript` | TypeScript 类型定义和编译器本身 |

此处的关键洞察是：**TypeScript 编译器是开发依赖**，这意味着用户安装 `@epheiamoe/licon` 后若执行 `postinstall` 编译，必须确保 Node.js 环境中能解析到 `typescript` 包。如果用户全局安装（`-g`），`postinstall` 会在全局 `node_modules` 中查找 TypeScript；如果项目本地安装，则在本地 `node_modules` 中查找。

## 可复现构建

由于 `dist/` 不纳入版本控制，且 `package-lock.json` 锁定了所有依赖版本（包括 TypeScript 编译器），理论上任何人在同一 Git 提交上运行 `npm ci` + `npm run build` 都能得到字节一致的构建产物。这种可复现性对于调试和审计至关重要。
