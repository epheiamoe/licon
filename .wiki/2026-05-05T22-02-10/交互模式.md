# 交互模式

运行 `licon` 不加任何参数，你会进入一个交互式图标选择器。它不像其他子命令那样面向 AI Agent 的脚本调用场景，而是专门为坐在终端前的人类使用者设计的——不需要记忆命令名、选项和参数格式，一切通过提示和选择完成。

## 进入入口：自动判断

当用户只输入 `licon`（不带子命令）时，`src/index.ts` 的 `process.argv.length === 2` 分支接管控制权。这个分支执行一个简单的状态判断：

1. **未配置** → 自动进入 `setupCommand()`，引导用户配置本地 lucide 仓库路径
2. **已配置** → 自动进入 `interactiveCommand(config)`，启动交互循环

[来源](src/index.ts#L76-L84)

这意味着首次运行 `licon` 时，用户会直接看到设置向导而无需手动敲 `licon setup`；配置完成后再次运行，则无缝进入交互界面。两种状态之间的过渡完全透明。

## 核心循环：readline 驱动的 CLI 界面

交互模式的核心是一个 `while (true)` 无限循环，使用 Node.js 内置的 `readline.createInterface` 构建交互终端：

```typescript
const rl = readline.createInterface({
  input: process.stdin,
  output: process.stdout
});

const askQuestion = (prompt: string): Promise<string> => {
  return new Promise((resolve) => {
    rl.question(prompt, (answer) => {
      resolve(answer.trim());
    });
  });
};
```

每次循环首先打印提示行，然后 `await askQuestion('> ')` 挂起等待用户输入。

[来源](src/commands/interactive.ts#L25-L36)

## 三种操作模式

用户在交互循环中可以输入三类命令，系统通过 `if/else` 链依次匹配：

### 1. 模糊搜索（默认路径）

输入的任意非保留字内容都会触发 `fuzzy.filter` 搜索。搜索前，所有的图标元数据（名称、分类、标签）被拼接成一条 `searchText` 字符串：

```typescript
return { name, cats, tags, searchText: `${name} ${cats} ${tags}` };
```

模糊搜索从这里提取匹配项。这种"全字段平铺"策略意味着搜索 `heart` 时，图标名 `heart`、所属分类 `medical` 中的匹配、标签 `heart` 中的匹配都会被命中。

搜索结果默认展示前 10 条，每条带编号和分类信息：

```
 1. heart [medical]
 2. heart-off [medical]
 3. heartbeat [medical]
```

[来源](src/commands/interactive.ts#L38-L51)

### 2. 浏览所有图标

输入 `list` 后，系统列出前 50 个图标的名称和分类。如果图标总数超过 50 个，底部会提示剩余数量并建议使用搜索缩小范围：

```
Showing all 1500 icons:

  activity [health, fitness]
  ...
  ... and 1450 more. Use search to narrow down.
```

[来源](src/commands/interactive.ts#L57-L68)

### 3. 按分类浏览

输入 `cat <category>` 会筛选出属于该分类的所有图标，输出格式为逗号分隔的列表：

```
Category "medical" (120 icons):

activity, air-vent, ambulance, bandage, ...
```

[来源](src/commands/interactive.ts#L70-L80)

### 退出

输入 `quit` 或 `exit` 关闭 readline 并返回 shell。

[来源](src/commands/interactive.ts#L49-L54)

## 选择与预览：从搜索到 SVG

这是交互模式区别于命令行模式的核心价值。搜索展示结果后，系统进入二次选择阶段：

```
Enter number to select, or any key to search again:
> 1
```

用户输入数字后，系统从结果数组中取回对应的图标对象，读取 SVG 文件内容并直接输出到终端：

```typescript
const selectedIcon = (results[num - 1] as any).original;
const iconPath = path.join(iconsDir, `${selectedIcon.name}.svg`);
const svg = fs.readFileSync(iconPath, 'utf-8');

console.log('📋 SVG for embedding:');
console.log(svg);
console.log(`✅ Icon "${selectedIcon.name}" ready!`);
```

选择的数字是 1-based，所以 `results[num - 1]` 取到正确项。预览完后，循环继续，用户可以继续搜索下一个图标。

[来源](src/commands/interactive.ts#L89-L99)

## 与命令行模式的对比

| 特性 | 交互模式 | 命令行模式（search / list / cat） |
|------|----------|-----------------------------------|
| 启动方式 | `licon` | `licon search <query>` |
| 搜索引擎 | `fuzzy.filter` 同搜索命令 | `fuzzy.filter` |
| 结果展示 | 前 10 条，带编号 | 可配置 limit，默认 5 条 |
| 选择能力 | 支持数字选择 → 预览 SVG | 无，仅输出文字 |
| SVG 预览 | 内置 | 需配合 `licon get` |
| 适用场景 | 手动探索、快速查找 | 脚本调用、AI Agent 集成 |
| 多关键词 | 不支持（单次输入单查询） | 支持逗号/空格多查询 |

[搜索图标](搜索图标.md#) 的命令行版本支持逗号和空格分隔的多关键词查询，而交互模式只处理单次输入。这是由于交互模式的设计假定用户会在循环中反复搜索，而不是一次性提交复杂查询。如果发现某个分类下的图标太多，交互模式也提供了按分类分组浏览的能力——具体分类列表可以通过 [浏览与管理](浏览与管理.md#) 中的 `licon categories` 查看。

## 一次典型会话

```
$ licon

🎨 Lucide Icon Picker

🔍 Search icons (or type "list", "cat <category>", "quit"):
> heart

Found 12 matches:

  1. heart [medical]
  2. heart-off [medical]
  3. heartbeat [medical]
  ...

Enter number to select, or any key to search again:
> 1

📋 SVG for embedding:
<svg ... >...</svg>

✅ Icon "heart" ready!

🔍 Search icons (or type "list", "cat <category>", "quit"):
> quit
Goodbye! 👋
```

整个过程不依赖任何外部进程——`readline`、`fuzzy.filter`、`fs.readFileSync` 全部是 Node.js 原生或轻量 npm 包。这意味着即时秒开，无启动延迟。

## 设计权衡

交互模式不缓存图标列表（每次调用都重新扫描 `icons/` 目录下的 JSON 文件），这意味着启动时会有一次性开销，尤其在本地 lucide 仓库图标很多时。作为对比，[搜索图标](搜索图标.md#) 的 `searchCommand` 使用了模块级缓存，但交互模式为了实现相对简洁且避免缓存无效问题，采用了每次都重新构建列表的策略。

[来源](src/commands/interactive.ts#L19-L24)

这也解释了为何交互模式不适合 AI Agent：它假定了一个耐心阅读的人类在终端前等待输出，而 Agent 更需要结构化的、可预测的、无状态的输出格式。[AI Agent 集成](ai-agent-集成.md) 中对此有详细说明。
